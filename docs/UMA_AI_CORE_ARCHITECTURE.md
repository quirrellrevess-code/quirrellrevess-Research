# UmaAI 核心架构与剧本策略设计

## 核心原则

UmaAI 是项目的决策核心。URADLL 是数据接入、解析与插件宿主层，不应把自动训练策略塞进通信插件中。每回合的动作必须由 UmaAI 根据当前状态、培育目标和剧本规则做出决定。

## 分层设计

1. **Game Adapter（URADLL 适配层）**：接收并规范化当前培育状态、可用行动、训练收益、失败率、伙伴和事件数据；不决定最优行动。
2. **UmaAI Core（决策核心）**：负责状态快照、候选行动表示、长期目标、公共约束、评分接口、决策解释和回放。
3. **Scenario Strategy（剧本策略）**：每个剧本独立实现状态扩展、行动候选、机制收益、资源转换和阶段目标。禁止假设所有剧本共用一套训练分数。
4. **Action Executor（执行层）**：把最终决策映射为经过验证的游戏操作；确认响应与状态变化，负责超时、重复提交保护和停止开关。
5. **Replay / Evaluation（评估层）**：使用真实采集样本离线回放，比较策略版本，记录决策理由与培育结果。

## 决策流程

每回合按以下顺序执行：

1. 验证状态完整性并识别剧本；未知剧本或关键字段缺失时降级为只输出建议。
2. 构建该剧本自己的候选行动集合，不能预先假定训练、休息、外出、比赛的可用性完全一致。
3. 由剧本策略计算当前行动的即时收益、专属资源变化、阶段任务进度及长期影响。
4. 由核心层应用公共约束，例如培育目标、状态合法性、行动风险上限和技能点使用策略。
5. 输出带有分数、关键因素和置信信息的决策；平分时使用明确且可复现的规则。
6. 在执行层可用且已验证时才提交动作；等待结果响应并更新状态，不因请求发出就认定成功。

## 剧本策略接口（概念设计）

每个策略至少需要实现：

- `CanHandle(state)`：判断是否支持该剧本与版本。
- `BuildCandidates(state)`：生成该状态下合法的行动候选。
- `EvaluateAction(state, action)`：解释该行动的即时与长期价值。
- `GetPhaseObjectives(state)`：根据剧本阶段给出当前优先目标。
- `ApplyObservedResult(previousState, action, result)`：根据真实结果校正模型。

具体类型、字段与接口签名要根据仓库使用的语言、运行时和实际游戏数据进一步定稿；当前文档定义的是架构约束，不代表上述接口已经实现。

## 策略模块边界

- 公共层只处理跨剧本通用的基础设施与安全约束，不负责用单一公式评判所有剧本的训练收益。
- 每个剧本独立维护资源机制、特殊行动、阶段目标、专属训练收益与行动优先级。
- 角色、支援卡、继承因子和培育目标属于策略输入；权重应可配置并可通过回放评估。
- 新剧本必须先完成数据字段和行动机制梳理，再启用自动决策；不能识别时应安全降级。

## 当前开发优先级

1. 建立与 URADLL 解耦的 UmaAI 核心数据模型和决策接口。
2. 盘点仓库中的现有 UmaAI 相关实现与历史策略；优先复用经过验证的算法，而不是重新造一个通用打分器。
3. 选择一个明确剧本作为首个垂直切片，贯通状态解析、剧本策略、决策解释和离线回放。
4. 通过真实状态样本验证之后，再扩展到第二个剧本，并保持策略隔离。
5. 在行动协议验证后接入自动执行。

## 验收标准

- 相同状态和相同策略版本产生确定、可解释的决策。
- 不同剧本通过不同策略实现处理其专属机制，而不是仅切换几个权重。
- 未知剧本、缺字段或状态冲突时不会盲目提交动作。
- 每次决策可以追溯候选行动、评分分项、选中理由、执行结果和策略版本。
- 策略收益通过离线回放与实际培育结果验证，不以代码数量作为进度指标。
